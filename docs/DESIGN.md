## Problem Statement

Firewall lifecycle management on Palo Alto (Strata Cloud Manager / Panorama / PAN-OS)
is manual, slow, and audit-hostile. Day-1 deployment (standing up device groups,
templates, baseline policy) is bespoke per environment. Day-2 rule changes flow through
tickets, GUI edits, and tribal knowledge, which produces rule sprawl, shadowed rules,
undocumented any-any allows, and no clean audit trail. The goal is a GitOps workflow
where intent is declared in Git, compiled to PAN-OS config, risk-classified, and applied
as automatically as is safe — with every change producing NIST-mappable evidence.

## Why This Matters (operational pain being removed)

- **Change latency:** rule requests take days through manual ticket + NetOps queue; the
  business waits on the firewall team for routine allows.
- **Rule sprawl & risk:** no automated detection of any-any, shadowed, redundant, or
  overly-broad rules. Risk accumulates faster than humans can audit it.
- **No source of truth:** running config drifts from any documentation; GUI edits during
  incidents are never reconciled back.
- **Audit burden:** every assessment (NIST SP 800-53 Rev.5 CM/AC/AU controls) is a manual
  evidence-gathering fire drill because change history lives in tickets and human memory.

## Status Quo

Requests arrive via ticket → NetOps engineer interprets → hand-edits in Panorama/SCM GUI →
commits and pushes to device groups → closes ticket. Evidence = whatever was typed in the
ticket. Drift, ordering, and dedup are managed by human diligence. No plan-preview, no
automated risk gate, no rollback beyond manual GUI revert.

## Scope & Non-Goals

**In scope**
- Day-1 provisioning: NGFW bring-up (VM-Series / CN-Series / hardware), bootstrap, licensing
  and subscription activation, content/PAN-OS baseline, and **onboarding to Strata Cloud
  Manager** (device registration, auth-key, folder/label assignment).
- Day-1 config baseline: declarative bootstrap of device groups / templates / folders /
  snippets + baseline network (interfaces, zones, routers, NAT) and baseline security policy
  for *net-new or migrated-in* scope.
- Day-2: intent-based rule change requests → compile → risk-tier → apply.
- Drift detection, break-glass, evidence bundles.

**Non-goals (explicitly deferred)**
- Reverse-engineering the entire brownfield rulebase into intent on day one (coexistence
  period instead — see Premise 4).
- Multi-vendor abstraction (Fortinet/Cisco). Palo-only for v1.
- Replacing SCM/Panorama as the management plane. GitOps sits *on top* of it.

## Locked Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Platform | Palo Alto **Strata Cloud Manager (SCM)** as single management plane | Existing estate + Cortex alignment |
| Managed devices | VM-Series (public cloud) + PA-series (hardware), both SCM-managed | One config model (folders/snippets/labels), no Panorama |
| Reconcile engine | **Terraform** (`panos` + `scm` providers) | `plan` = PR preview + drift detector; `git revert` = rollback |
| Logic layer | **Python** (`pan-os-python`) | Compiler, risk classifier, evidence gen — all need real code + tests |
| Change model | **Risk-tiered auto-apply** | Speed where safe, human gate where dangerous |
| Intake | **Intent abstraction** (declared intent → compiler → PAN-OS) | Best self-service; strongest audit story |
| Risk classifier | **Built in-house** (Python policy-as-code) — no commercial tool owned | Semantic checks need current-policy context; Rego awkward for stateful decisions |
| VM-Series pilot clouds | **AWS + GCP** (skeleton on one first, then the second front door) | Two bootstrap mechanisms, one shared SCM spine |
| CI/CD + governance | **GitHub Actions** (OIDC to Palo, environment protection for the approval gate) | Run history + RBAC + scheduling; also hosts the intake (Issue Forms → PR) |
| Evidence + SSoT | **Git** — evidence bundles Git-resident, Git is authoritative | Self-consistent audit story; no external evidence store to reconcile |
| Requesters | **Broad** (not just engineers) | Intent schema must speak app/business language; compiler resolves all firewall internals |

Ansible was evaluated and dropped: Terraform already owns state, and the intent compiler is
software that belongs in Python, not Jinja. Ansible only earned a place via AWX/Tower's
governance layer, which the CI platform now provides.

## Architecture

```
Requester
   │  (declares intent: src, dst, service, app, justification)
   ▼
Intent YAML (in Git)  ──PR──▶  CI pipeline
                                  │
                                  ├─ 1. Python compiler (pan-os-python)
                                  │     intent → PAN-OS objects, dedup,
                                  │     device-group/vsys targeting, rule placement
                                  │
                                  ├─ 2. Risk classifier (policy-as-code)
                                  │     any-any / shadowed / broad CIDR-service /
                                  │     novel zone-pair  →  risk tier
                                  │
                                  ├─ 3. Terraform plan (panos/scm)
                                  │     desired-state diff + drift check
                                  │
                                  ├─ 4. Evidence bundle (NIST-mapped)
                                  │
                                  ▼
                        Risk tier gate:
                          low  → auto-merge + auto-apply
                          high → human approval → apply
                                  │
                                  ▼
                        Terraform apply → SCM/Panorama commit-and-push → PAN-OS
```

Git is the source of truth. The running config is **not** trusted (see Premise 2).

## Premises (agreed working assumptions)

1. **The intent compiler is the crown jewel, not Terraform.** ~70% of build effort is the
   intent→PAN-OS compiler (dedup, device-group/vsys targeting, rule placement/ordering,
   service normalization). Terraform is the easy part.
2. **Git is source of truth; running config is not trusted.** Default drift stance is
   *detect-and-alert + scheduled reconcile-with-approval*, never blind overwrite (a hard
   reconcile could wipe a legitimate emergency change).
3. **Policy-as-code is a hard prerequisite for risk-tiering.** No commercial risk engine is
   owned (AlgoSec/Tufin/FireMon absent), so the classifier is **built in-house** (Python) and
   lands in Phase 2. It shares a current-policy state model with the compiler (both read SCM).
4. **Brownfield rulebase stays out of the automated loop initially.** Wrap net-new +
   migrated scope; coexistence period is mandatory.
5. **"Fully automatic" has a hard floor: sanctioned break-glass + fast rollback must exist.**
   Otherwise people bypass GitOps under pressure and drift explodes.

## Approaches Considered

### Approach A — Walking Skeleton (spine-first)
Thinnest end-to-end enforcing path: minimal intent schema → compiler for 1-2 common change
types → Terraform on one greenfield device group → CI plan preview → PR + human approval
always → apply on merge. Detect-only drift. Break-glass documented.
Effort S-M · Risk Low. Proves the pipeline before the big compiler/policy investment.

### Approach B — Full Platform (ideal architecture)
Everything at once: rich intent schema, full compiler (SCM + Panorama backends,
multi-device-group), policy-as-code risk classifier driving risk-tiered auto-apply,
detect-and-alert drift + scheduled reconcile, break-glass with evidence, NIST-mapped
bundles, self-service intake.
Effort XL · Risk Med-High. Delivers the full ask but long road to first value; two hard
things (compiler + risk engine) must both land before auto-apply is safe.

### Approach C — Borrow the Risk Engine (buy-vs-build hybrid)
Git + Python own intent + compilation; offload risk analysis and change simulation to a
commercial engine (AlgoSec/Tufin/FireMon) or Palo BPA/Prisma AIOps via API. Its verdict
sets the risk tier. Skips building the classifier.
Effort M if tool owned / N/A if not · Risk Low-Med. Fastest path to *trustworthy*
auto-apply; hard dependency on owning the tool + vendor coupling.
**NOT TAKEN** — no commercial tool owned; classifier is built in-house (see Recommended Approach).

## Recommended Approach

**A→B phased roadmap, with C as a fork on the risk-engine component.**

- **Phase 1 — Walking Skeleton (Approach A).** One greenfield device group, minimal intent
  schema, compiler for address-object + scoped-allow, Terraform reconcile, CI plan preview,
  human approval on every change, detect-only drift, documented break-glass. Goal: prove
  the pipeline enforces correctly with tiny blast radius. Ships in weeks.
- **Phase 2 — Risk-tiering + evidence (toward B).** Build the Python risk classifier (no
  commercial tool to borrow), turn on risk-tiered auto-apply for low-risk classes, ENRICH the evidence
  bundle with the risk section (tier, fired checks, classifier + threshold versions), add
  detect-and-alert drift with scheduled reconcile-with-approval.
  *(Correction 2026-07-19: the evidence bundle BASELINE is Phase 1, not Phase 2 — the
  Phase-1 success criterion requires it, and it is the audit story that justifies the
  platform. Built and tested in `fwgitops.evidence`; Phase 2 only fills `risk`.)* Heaviest phase — the classifier is the critical-path build here.
- **Phase 3 — Scale + self-service (full B).** Expand compiler to SCM + Panorama backends
  and multi-device-group targeting, widen intent schema, add self-service intake surface,
  onboard additional device groups, formalize break-glass with automated evidence capture.

**Risk-engine fork — RESOLVED: build.** No commercial firewall-analysis tool is owned, so
Approach C's borrow-the-verdict shortcut is off the table. The Python policy-as-code
classifier is built in-house and lands in Phase 2. This is the second-hardest build after the
compiler and sits on the critical path to auto-apply, but Phase 1 (human-approval-always) is
unaffected — the skeleton ships on the same timeline.

## Design Detail — Day-1 Provisioning & SCM Onboarding

Provisioning is a distinct workstream from rule changes. It gets a firewall from "boxed or
booted" to "SCM-managed and enforcing a baseline," ideally zero-touch. **SCM is the single
management plane for both VM-Series and PA-series** — one config model (folders / snippets /
labels), the `scm` provider + SCM REST API, one onboarding concept (device auth-key → folder).

### One SCM spine, two front doors

The onboard + baseline layer is **shared** across form factors. Only instantiate + phone-home
differ:

```
VM-Series (cloud) ─┐
                   ├─▶ SCM onboard (device auth-key → folder/label) ─▶ baseline snippet stack ─▶ enforcing
PA-series (HW)    ─┘
      │                          (shared spine — build once)
   front doors differ:
    • VM-Series: Terraform instantiates + bootstrap package → auto phone-home
    • PA-series: manual rack/cable → ZTP → claim into SCM tenant (serial pre-registered)
```

Build the SCM onboard+baseline spine once; the two front doors plug into it.

### Provisioning steps (in order)

1. **Instantiate.** VM-Series on **AWS + GCP** (kept as separate Terraform submodules —
   `provisioning/terraform/aws`, `.../gcp` — feeding the shared SCM module; no cloud-agnostic
   abstraction). AWS: init-cfg via EC2 user-data or S3 bootstrap bucket + IAM role, VPC/subnets/
   SGs, mgmt + dataplane ENIs. GCP: init-cfg via instance metadata or GCS bootstrap bucket +
   service account, VPC/firewall-rules, mgmt + dataplane NICs. PA-series: physical rack/cable
   (manual) + serial pre-registered in the SCM tenant. **Skeleton builds one cloud first**
   (AWS-first if it's a coin flip), then the second front door.
2. **Phone home / bootstrap.** VM-Series: bootstrap package — `init-cfg.txt` (mgmt, DNS,
   hostname, SCM onboarding params / device auth-key) + minimal `bootstrap.xml`. PA-series:
   ZTP pointed at SCM. Either way the device claims into the SCM tenant with no console step.
3. **License + subscriptions.** Activate via deployment profiles / credit pools (CSP/SCM):
   Threat Prevention/ATP, Advanced URL, WildFire, DNS Security. Python retry-and-verify loop
   (this is the flakiest step for both form factors).
4. **Onboard to SCM.** Consume the device auth-key, assign the device to the correct
   **folder/label**, bind the config scope (snippet stack that carries baseline). `scm`
   provider where it covers the object; raw SCM REST API in Python where it doesn't.
5. **Push network + security baseline.** Interfaces, zones, logical routers, baseline NAT,
   mgmt-profile lockdown (permitted IPs), admin RBAC, logging to Strata Logging Service /
   Cortex Data Lake. Delivered as an SCM **snippet stack** — start from **Iron-Skillet** /
   BPA-aligned best-practice config, parameterized per site, not authored from scratch.
6. **Content + PAN-OS floor.** Ensure dynamic updates (apps/threats, AV, WildFire) and a
   minimum PAN-OS version — for PA-series this may require an upgrade *before* it can claim
   into SCM (version check in the hardware front door).

### Engine split for Day-1

- **Terraform (`scm`):** VM instance + mgmt networking + bootstrap storage; SCM folders +
  snippet stacks + baseline config.
- **Python (SCM REST API):** auth-key generation, license/subscription activation (retry
  loop), content-update trigger, "wait until connected" verification, post-onboard health
  check, evidence bundle, and any SCM object the `scm` provider doesn't yet cover.
- **Bootstrap artifact:** `init-cfg.txt` generation (templated), uploaded by Terraform.

### Idempotency reality

A firewall is long-lived and stateful, unlike a rule. Re-running provisioning must NOT
re-bootstrap. Terraform tracks the instance; "is it onboarded + baseline-current?" is a
**runtime check** (Python queries SCM), not TF state. Day-1 needs a small reconcile-and-verify
step TF alone won't give you.

### Gotchas / order-of-operations

- License → content/version → baseline config (App-IDs need content present first).
- Keep `bootstrap.xml` minimal (enough to onboard only); push the real baseline from SCM so
  Git stays authoritative and the two don't conflict.
- PA-series "zero-touch" is zero-*config*-touch, not zero-*hands* — power, cabling, mgmt
  reachability, and serial pre-registration are prerequisites.
- `scm` provider coverage is now load-bearing (single plane) — validate against the baseline
  snippet set in week one; Python REST is the fallback.

**Evidence:** provisioning emits its own bundle (device identity/serial, auth-key issuance,
license state, baseline config hash, PAN-OS/content versions, onboarding timestamp, who
triggered) — core controls plus **CM-2** (Baseline Configuration) and **CM-6** (Configuration
Settings).

**Phase-1 sequencing:** build the shared SCM spine on **VM-Series first** (disposable,
loop-in-code), prove boot → bootstrap → SCM onboard → baseline end-to-end, then add the
**PA-series front door** (ZTP + version check) into the same spine. Day-2 rule flow comes
after the pilot firewall is enforcing.

## Design Detail — Day-2 Intent Schema & Compiler

**Principle: the requester speaks app, the compiler speaks PAN-OS.** Requesters are broad, so
the schema forbids firewall internals. If a requester ever types "zone" or "device-group," the
schema failed.

| Requester provides | Compiler derives |
|---|---|
| environment, source, destination, service, justification, ticket | SCM folder, source/dest zones, address/service objects, rule position, dedup, naming, log profile |

### Intent schema (v1)

```yaml
# intent/<environment>/<app>/REQ-2026-0417.yaml
apiVersion: fw-intent/v1
kind: AccessRequest
metadata:
  id: REQ-2026-0417            # unique; the change record key
  requester: jane.doe@corp     # or derived from PR author (Git = identity)
  ticket: JIRA-12345           # mandatory — audit linkage
  justification: "Web tier needs to reach the payments API"
  requested: 2026-07-19
spec:
  environment: prod            # → resolves to SCM folder + zone context
  action: allow                # allow | deny
  source:
    - app: web-tier            # named catalog entity …OR…
    - cidr: 10.20.1.0/24       # explicit fallback
  destination:
    - app: payments-api        # named catalog entity …OR…
    - fqdn: payments.internal  # explicit fallback
  service:
    - name: https              # service catalog → tcp/443 …OR…
    - protocol: tcp
      port: 8443
  log: true
```

The `cidr`/`fqdn` and raw `protocol/port` escape hatches keep the schema usable before the
catalogs are complete and let power users be explicit. The **catalog** (app→subnets/zones,
service→port) is platform-maintained config the compiler resolves against — it's what lets a
broad requester say `app: payments-api` instead of a subnet. Catalog resolution is what makes
"broad requesters" real; explicit CIDR/FQDN is the Phase-1 fallback while the catalog fills in.

### Compiler pipeline (11 stages)

1. **Parse + schema-validate** (pydantic / JSON-schema) — reject malformed early with a helpful
   PR comment.
2. **Resolve entities** — app→objects, environment→folder+zones, service→ports (via catalog).
3. **Normalize** — canonicalize CIDRs, dedup/expand services and groups.
4. **Infer zones** — IP-to-zone map per environment (requester never sees this).
5. **Dedup vs current policy** — pull current SCM state; reuse objects, detect exact-dup rules.
   *Shares the current-policy state model with the risk classifier — build once.*
6. **Object management** — create objects only if absent; deterministic naming.
7. **Synthesize rule** — folder scope, from/to zone, src/dst/svc, action, log, tags
   (REQ-id + ticket + section). No expiry tag — expiry is not modelled, see below.
8. **Placement** — position to avoid shadowing (specific-before-general; structured rulebase
   sections).
9. **Emit artifact** — data for Terraform (see output contract below).
10. **Risk classify** (Phase 2) — tier the change.
11. **Evidence bundle** — intent→objects→rule→placement, Git-resident.

Stages 2, 4, 5, 8 hold the real engineering. **Determinism is the rule:** the same intent
compiles to the same output, so re-runs are safe and diffs are clean.

### Compiler → Terraform output contract (DECIDED: data-driven `for_each`)

The compiler emits **data** (`rules.auto.tfvars.json`, per folder); a hand-written **static**
Terraform module iterates with `for_each`. Generated content is data, never code. Benefits:
clean readable PR diffs, compiler testable without a Terraform toolchain (assert on JSON), and
the module is reviewed once and human-owned.

**Critical discipline:** `for_each` keys must be **stable** (use REQ-id or a deterministic
hash), or Terraform churns/recreates rules when the collection shifts. Get this right on day
one — it is the one thing that bites later.

## Design Detail — Rulebase Analysis Core (dedup · shadow · placement)

Stage 5 (dedup), stage 8 (placement), and the risk classifier's shadow/redundancy checks are
**the same analysis engine** viewed three ways. Build it once; all three consume it.

### Effective rulebase model (SCM-aware)

PAN-OS evaluates security rules **top-down, first-match**. SCM adds folder hierarchy, so the
real evaluation order is **ancestor pre-rules → local rules → ancestor post-rules** (plus
snippets). The state model must materialize the **effective ordered rulebase** for a folder
after inheritance, not just local rules. One SCM reader builds it; stage 5, stage 8, and the
classifier all consume it (this is the shared current-policy state model).

Each rule is a 5-tuple of **sets**:
`(from-zone, to-zone, source IP-set, dest IP-set, service port-set [, app-id])` — IP sets via
`netaddr`/`IPSet`, services as port-range sets, zones/apps discrete. Shadow analysis is then
set algebra.

### Three verdicts

- **Redundant** — a broader *allow* above already covers R's whole match set → dedup to no-op
  (stops sprawl; this is stage 5).
- **Shadowed** — a rule above fully covers R with a blocking/different action → R never
  matches (silent breakage).
- **Partial shadow** — match sets overlap, neither is a superset → the subtle, dangerous case.

Set-subset + set-intersection over the 5-tuple yields all three.

**Known limitation (state it to auditors):** App-ID (L7) overlap can't be fully computed
statically. **v1 does service/port-based shadow analysis; App-ID-aware shadowing is a gap** the
risk classifier flags for human review rather than pretending to resolve.

### Placement — sectioned rulebase (DECIDED)

**Cardinal rule: never auto-reorder existing rules.** Moving an existing rule silently changes
evaluation for live traffic — outage or hole nobody reviewed. New-rule placement is safe;
reordering is a high-risk, human-gated act, always.

Instead of computing an "optimal" global position, impose a **sectioned rulebase**:

```
Section 1: infrastructure / deny-known-bad   (top)
Section 2: specific allows                    ← most compiled rules land here
Section 3: broad / infrastructure allows
Section 4: default deny + log                 (bottom)
```

New rule → **specificity score** (below) → placed within its matching section,
specific-before-general. Shadow validation runs on the resulting order and **flags** conflicts
for human review — never silently fixes them. Section membership is a tag, which also yields
stable `for_each` keys.

### Specificity score (deterministic)

Weighted sum of per-dimension narrowness; narrower ranks higher within a section:

| Dimension | Most specific → least |
|---|---|
| source / destination | host `/32` → small CIDR → large CIDR → any |
| service | single port → port range → any |
| zones | named zone → any |
| app | specific App-ID → any |

`any` in any field tanks the score (sinks broad rules toward Section 3). Tie-breaker is
stable (REQ-id / requested-timestamp) so ordering is fully reproducible: same inputs → same
order, every compile.

## Design Detail — Risk Classifier (three-tier, DECIDED)

The classifier is **thin**: policy on top of the analysis core, not new analysis. It takes a
compiled change + the core's verdicts and outputs a **tier + a human-readable reason**.

**Engine: Python, not OPA/Rego.** The hard checks are *semantic* — they depend on the current
compiled rulebase (shadow/redundancy, novel-zone-pair), so the classifier queries existing SCM
state via the **shared current-policy state model** (built once, with the compiler). Rego is
clean for stateless allow/deny tables but awkward for state-dependent decisions. Tunable
thresholds live in security-owned YAML; the logic stays Python.

### Inputs (invents nothing)

Compiled rule(s) (5-tuple sets, action, app, zones, folder/env) · analysis-core verdicts
(redundant / shadowed / partial / placement-conflict) · current effective rulebase (novelty
checks) · intent metadata (env, ticket) · catalog context (critical-asset tags).

### Check set — a rule table, most-severe-wins

Each check is deterministic `f(change, state) → (fired?, severity, reason)`. Tier = the max
severity that fires.

**CRITICAL (escalate — security/senior sign-off, never auto-eligible):**
- any-any (any-source **and** any-dest) in one rule
- `any` combined with a permissive/critical zone (untrust→trust, internet ingress)
- management-plane exposure (dest = mgmt network/service)
- critical-asset destination (catalog tag) with a broad source
- deny weakened or removed (deny→allow, or a deny narrowed)

**HIGH (standard human review):**
- novel zone-pair (from/to not in current effective rulebase)
- broad CIDR (prefix shorter than configured cutoff)
- broad / high-risk service (wide port range, or 22/3389/etc. from a broad source)
- partial-shadow verdict from the core
- App-ID rule the static analysis couldn't fully verify (the known L7 gap)
- any structural prod change
  (the original "permanent rule (no expiry) above a sensitivity threshold" signal is
  DROPPED with the expiry field — every rule is now permanent, so it would fire on all
  of them and mean nothing)

**LOW (auto-apply eligible):**
- fully-scoped allow (specific src/dst, single service, known zone-pair, lower-sensitivity env)
- tightening an existing rule; adding a member to an approved group
- redundant verdict → compiles to no-op

### Tier → GitHub Actions gate mapping (separation of duties)

| Tier | Gate | NIST |
|---|---|---|
| **LOW** | auto-merge + auto-apply after CI pass | CM-3 |
| **HIGH** | standard approver (folder CODEOWNERS) via environment protection, then apply | CM-3, CM-5 |
| **CRITICAL** | security/senior **dual-control** environment; never auto even with a fast-path | AC-5, CM-3, CM-5 |

Each tier targets a different GitHub Actions **environment** with its own required reviewers.

### Two non-negotiables

1. **Fail closed, always.** On classifier error, unreadable SCM state, or any uncertainty →
   return the *most restrictive* tier and route to human review. If the analysis core couldn't
   build the effective rulebase, LOW **cannot** be certified. A fail-open classifier auto-applies
   an unreviewed change — the one bug that ends the project.
2. **Explainable + versioned.** Every verdict emits its fired checks + reasons into the PR
   comment and evidence bundle (*"HIGH: novel zone-pair dmz→app; broad source 10.0.0.0/8"*), and
   records the **classifier + threshold-table version** that evaluated it, so a past decision is
   reproducible after the rules change (CM-3, AU-2). Threshold changes are PRs.

**Testing:** a golden set of intents → expected tiers, regression-tested. A mis-tier that calls
a dangerous change LOW = an auto-applied hole, so this test set is a release gate, not optional.

## Design Detail — Apply Cadence & Scheduling (DECIDED)

Apply cadence is **tier-driven**, and two axes are kept independent: **windowing** controls *when*
a change may apply; **batching** controls *how many* changes per commit. Decision: windowing gates
timing; **isolation stays 1:1 (one change per commit) at every tier**. Batching is OFF by default.

| Tier | When it applies | Grouping |
|---|---|---|
| **LOW** | continuous, on merge | 1 change / commit |
| **HIGH** | within change hours (window gates timing only) | 1 change / commit, applied **sequentially** |
| **CRITICAL** | scheduled maintenance window + security sign-off | 1 change / commit, **isolated** |

**Why 1:1 everywhere:** it preserves the clean per-change rollback + candidate/commit boundary from
"Change Rollback & Cancellation." Batching (N changes per commit) would buy fewer SCM pushes at the
cost of per-change rollback and blast-radius isolation (revert-the-batch or bisect-the-batch). So a
HIGH change window applies multiple approved changes **as N sequential commits, never one bundled
commit.**

**Batching is an opt-in optimization only** — reach for it solely if SCM commit/push overhead proves
a real bottleneck, and **never for CRITICAL**.

**Scheduler is window-aware but windows are configurable.** If the org mandates maintenance windows for
firewall changes, HIGH/CRITICAL respect them; if not, they apply on approval without waiting. Building
the scheduler window-aware from the start avoids rework either way. (Open input: confirm the org's
change-window policy for prod.)

## Design Detail — Drift Detection (tag-scoped reconciliation, DECIDED)

Git is SSoT, so any divergence between SCM's running config and Git desired-state is drift.
Detect-and-alert by default; reconcile only with approval.

### Three drift classes

| Class | What happened | Handling |
|---|---|---|
| **Modification** | a managed rule edited in SCM | plan/diff shows update-back-to-desired |
| **Deletion** | a managed rule deleted in SCM | diff shows re-create |
| **Additive** | a rule *added* out-of-band in SCM | the dangerous one — see detector below |

### Why `terraform plan` alone is insufficient

Terraform only sees resources in its state. A rogue rule added in the SCM GUI was never in TF
state, so `terraform plan` won't flag it — unless TF is authoritative over the *whole* folder,
which means importing the brownfield rulebase and **contradicting Premise 4**. So the most
dangerous drift (out-of-band any-any) is exactly what a naive plan misses.

### Detector: tag-scoped reconciliation diff (reuses the analysis core)

The detector compares the **compiled desired-set** (all Git intents for the folder) against the
**SCM effective rulebase**, scoped to platform-tagged managed rules. It reuses the shared
current-policy state model + set algebra.
- managed rule changed/deleted → modification/deletion drift
- a rule present in a managed folder **lacking the gitops tag** that wasn't there before →
  additive drift (this is how rogue rules are caught while brownfield is ignored)
`terraform plan -detailed-exitcode` corroborates the TF-managed subset as a secondary check.

### Flow: detect → attribute → decide → reconcile

```
scheduled GitHub Action (per folder, cadence by sensitivity)
  ├─ detect ...... compiled desired-set vs SCM effective rulebase (tag-scoped)
  ├─ attribute ... correlate drift timestamp with SCM config-version/audit log → who + when
  ▼
drift → open DRIFT PR/issue (diff + class + attribution) + Slack/Teams alert
  ▼
human decides (never auto):
   • legitimate (e.g. break-glass) → BACK-FILL into Git intent (codify into SSoT)
   • unauthorized/mistake         → RECONCILE: apply Git desired-state back (revert)
```

- **Attribution needs the SCM audit log**, not just the plan: plan says *what*, SCM
  config-version history says *who/when* — essential for the evidence bundle (AU-6) and for the
  legitimate-vs-rogue decision.
- **Reconcile is a gated apply.** Reverting an unknown rule can be high-risk (it may be
  load-bearing), so route the reconcile action back through the classifier + tier gates — never
  treat "revert to desired" as automatically safe.
- **Drift SLA.** A resolution window (tighter for prod/DMZ); unresolved drift past the window
  escalates — persistent prod drift is an incident. This keeps Git honest as SSoT.

**Evidence:** each drift event emits an entry (what drifted, class, attribution, resolution =
back-filled or reverted, approver, timestamps) — CM-3 (catching unauthorized change), CM-6,
AU-6.

### Two-level drift: SCM AND device (DECIDED)

Drift exists at two layers, and the tag-scoped detector above only sees Level 1:

```
Git (intent)        ← Level 1: SCM config vs Git desired      (tag-scoped reconciliation, above)
   │ push
SCM (config)        ← Level 2: device running config vs SCM   (the blind spot below)
   │ push
Firewall (running)  ← direct box edit, or local rules outside SCM, or a silently failed push
```

**Level 2 is the dangerous blind spot:** SCM believes config is X; someone with device access made
a local change (or a push failed), so the box enforces Y. GitOps and Level-1 detection both see X.

**Prevention-first (the strong control): lock down direct device access.** The Day-1 baseline
restricts local admin/config on SCM-managed devices — SCM is the only write path, direct access only
via logged break-glass, admin RBAC so humans don't log into the box. This shrinks the Level-2 surface
to essentially break-glass. NIST **CM-5 / AC-3**. The Iron-Skillet/BPA mgmt-lockdown baseline *is* the
Level-2 prevention.

**Posture (DECIDED): start tiered, converge to hard lockdown.** Hard-lockdown prod/crown-jewel first;
allow local access + detection on lower-sensitivity tiers initially; migrate all SCM-managed devices
toward hard lockdown over time.

**Detection backstop:** poll SCM **device sync / out-of-sync status** (cheap, catches push
failures/mismatches) + alert. For crown-jewel devices, periodic **running-config retrieval + diff**
against pushed config to catch local rules SCM doesn't track. Same posture as Level 1:
detect-and-alert, reconcile-with-approval (a re-push could wipe a legitimate break-glass change),
back-fill break-glass into Git.

## Design Detail — Change Rollback & Cancellation (DECIDED)

"Cancelled" is four distinct events with different rollback semantics:

| Cancel point | What's applied | Rollback |
|---|---|---|
| **Pre-merge** (PR rejected/withdrawn) | nothing | trivial — close PR; the gate ensured no apply ran |
| **Mid-apply** (job cancelled, runner dies, abort) | partial | candidate/commit boundary — see below |
| **Post-apply** (bad change found later) | fully live | `git revert` intent → recompile → plan removes it → apply |

**Mid-apply atomicity — candidate/commit transaction boundary. CONFIRMED by the spike
(2026-07-19):** the `scm` provider has NO push/commit capability, so Terraform can only
stage config — a separate push (**target = folder**) makes it live. The boundary is
structurally forced, not just a design preference. Terraform `apply` **stages** config;
a separate controlled **commit/push** step is the atomic point.
- Cancel **before** commit → discard the candidate → nothing was ever enforced (clean auto-rollback).
- Cancel **after** commit → change is live → post-apply path (git-revert + re-apply), with an SCM
  config-version snapshot as the fast break-glass escape during an incident.

**Ordering rule:** create objects before rules, so a rule never references a half-built object; orphan
objects from a cancel are harmless and swept by the next reconcile.

**Folder-scoped push (spike finding #10).** A push commits EVERYTHING staged in the folder,
not just our change. Two safeguards: (a) applies are serialized per folder so the pipeline
never stages two changes at once (preserves 1:1 isolation + clean rollback); (b) the push
step FAILS CLOSED if unexpected staged changes are present — committing an out-of-band GUI
edit under our audit trail would be worse than stopping. That staged delta is Level-1 drift.

**Rule expiry is NOT modelled (removed 2026-08-05).** An optional `expires:` field existed on intent
metadata and was retired: nothing enforced it. It never reached the firewall, no job removed an
expired rule, and on a Day-1 kind it was parsed and dropped entirely because evidence bundles are
`AccessRequest`-only. A field that means nothing is worse than a missing one — a reader assumes it
means something, and the evidence bundle asserted a date nobody honoured.

It is now REJECTED at PR time rather than ignored, because this loader drops unknown metadata keys
silently and a bare deletion would have turned every existing `expires:` into a no-op.

PAN-OS does have real, device-enforced rule expiry (`scm_security_rule.schedule` → an `scm_schedule`
with `non_recurring` date ranges). That is a separate capability this platform does not wire; note
that a lapsed *allow* stops matching and traffic then falls through to whatever sits below it, so it
is only fail-closed if rule ordering says so.

Git stays authoritative throughout: the SCM snapshot restore is a break-glass escape only (it bypasses
Git and creates Level-1 drift that must then be back-filled).

## Design Detail — Break-Glass

Sanctioned emergency path: a separate, logged, time-boxed workflow that lets an authorized
engineer push a change fast, while still capturing who/what/why/when as evidence. Post-hoc,
the change must be reconciled into Git intent within a defined window or it flags as drift.
Break-glass is a feature, not a bypass.

## Design Detail — Evidence & NIST Mapping

Each change emits a structured evidence bundle (JSON) linking intent, compiled config, risk
verdict, approver, plan diff, apply result, and timestamps. Primary control coverage:
- **AC-4** (Information Flow Enforcement) — the rule change itself + risk classification
- **CM-3** (Configuration Change Control) — PR + approval + audit trail
- **CM-5** (Access Restrictions for Change) — CI RBAC + environment protection + OIDC
- **AU-2 / AU-12** (Audit Events / Audit Generation) — evidence bundle + CI run history
- **SC-7** (Boundary Protection) — enforced policy state itself
